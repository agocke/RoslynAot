# RoslynAot

RoslynAot is an experimental NativeAOT compiler host and analyzer ABI. The
compiler host runs real Roslyn with a proxy `DiagnosticAnalyzer`. Analyzer
registrations, callbacks, Roslyn object queries, and diagnostics cross a
versioned, `IUnknown`-style C ABI generated by `ComWrappers`. Managed Roslyn
objects never cross the module boundary.

See [ROADMAP.md](ROADMAP.md) for the package goal, completion criteria, and
remaining product work.

The cross-runtime compatibility problems that must be solved for arbitrary
analyzers are listed in the
[analyzer remoting problem inventory](docs/ANALYZER-REMOTING-PROBLEMS.md).

Engineering details are documented with their owning components:

- [Native ABI and marshalling semantics](src/RoslynAot.Abi/README.md)
- [Analyzer-side runtime](src/RoslynAot.AnalyzerRuntime/README.md)
- [C# compiler](src/CscAot/README.md)
- [Roslyn facade generator](tools/RoslynAot.RoslynFacadeGenerator/README.md)

The current prototype:

- NativeAOT-compiles a Roslyn-based C# compiler host.
- Compiles every C# analyzer in an unchanged, prebuilt Roslyn analyzer assembly
  into one NativeAOT shared library.
- Supplies public-signed facade assemblies named `Microsoft.CodeAnalysis` and
  `Microsoft.CodeAnalysis.CSharp` to satisfy the analyzer's existing strong-name
  references.
- Presents a real `DiagnosticAnalyzer` proxy to compiler-side Roslyn and a
  Roslyn-compatible managed facade to the analyzer.
- Generates analyzer and host vtables, proxies, and dispatch thunks from
  `[GeneratedComInterface]` interfaces.
- Uses build-time metadata inspection to generate deterministic analyzer
  factories and a multi-analyzer native module entry point.
- Transports action registration, syntax callbacks, object handles, and
  diagnostics through `StrategyBasedComWrappers` proxies.
- Packs build-transitive MSBuild targets that publish the compiler host and
  opt-in analyzer projects.

The sample analyzer is compiled normally against the official Roslyn package;
the NativeAOT wrapper consumes its resulting DLL without rebuilding or rewriting
it. The SDK `Microsoft.CodeAnalysis.CSharp.NetAnalyzers.dll` is inspected at
build time and all 43 C# analyzers are linked into one native module. CA1200
runs unchanged through that module, including localized descriptors,
polymorphic Roslyn facade returns, XML syntax inspection, and diagnostic
locations.

## Build and run

```bash
dotnet publish src/CscAot -r linux-x64 -c Release
dotnet build samples/RoslynAot.SampleAnalyzer -c Release
dotnet publish samples/RoslynAot.SampleAnalyzer.Native -r linux-x64 -c Release
dotnet publish samples/RoslynAot.CSharpNetAnalyzers.Native -r linux-x64 -c Release
```

Run the compiler with reference assemblies supplied by the build:

```bash
csc-aot \
  /nologo \
  /nostdlib+ \
  /target:library \
  /out:artifacts/Bad.dll \
  /reference:/path/to/System.Runtime.dll \
  /analyzer:/path/to/roslyn-aot-sample-analyzer.so \
  samples/Bad.cs
```

The arguments are parsed by Roslyn's `CSharpCommandLineParser`, including
response files produced by MSBuild. Analyzer preparation occurs before this
invocation, so every `/analyzer:` value received by the native compiler is
already a platform-native shared library.

Analyzer libraries remain loaded for the compiler process lifetime because
`ComWrappers` proxies can release their native references during garbage
collection.

Validate the SDK-shipped CA1200 analyzer against the managed compiler on Linux
x64:

```bash
bash eng/validate-ca1200.sh
```

The command NativeAOT-publishes the compiler and the whole C# NetAnalyzers
module, compiles the same source through both paths, and requires an identical
CA1200 diagnostic, documentation output, and emitted assembly. It also prints
`AD0001` diagnostics from onboarded analyzers whose registration kinds are not
implemented yet, making those compatibility gaps available for follow-up
testing.

Validate the sample analyzer module, including the analyzer failure path:

```bash
bash eng/validate-sample-analyzer.sh
```

The command compiles `samples/Bad.cs` and requires the expected `AA0001`
diagnostic, then compiles `samples/Throwing.cs` and requires that the
deliberately throwing sample analyzer surfaces an `AD0001` diagnostic naming
the analyzer type, action kind, and exception — without failing the build or
losing the compiled output.

## Package integration

`RoslynAot.Experimental` currently publishes the NativeAOT compiler host before
`CoreCompile`. The analyzer preparation target will accept existing analyzer
DLLs, run the metadata entry-point generator, publish static NativeAOT wrapper
projects, then replace the `@(Analyzer)` items passed to `Csc` with the resulting
native module paths. The compiler host derives from Roslyn's internal
`CSharpCompiler` and resolves each module into one compiler-side proxy per
generated analyzer factory; it does not use managed analyzer reflection.

```xml
<ItemGroup>
  <RoslynAotAnalyzer Include="path/to/ExistingAnalyzer.dll" />
</ItemGroup>
```

Replacing the SDK's `Csc` task is intentionally not enabled yet: the internal
driver path works, but the package still needs analyzer preparation, caching,
compiler-tool wiring, and Roslyn-version compatibility checks.
